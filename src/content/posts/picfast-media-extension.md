图床跑稳之后，很自然会想让它顺手把视频和音频也托管了。真开始摸底才发现，难点不在上传按钮，而在一个很底层的假设上：现有的图片链路默认「文件可以整个读进内存」。单文件上限要做到 1GB，这个假设第一个就不成立。

这篇是动手改代码之前的调研记录：现有系统长什么样、为什么不能直接复用图片模块、打算怎么加、以及哪些坑必须先绕开。

> [!NOTE] 先说清楚本文的状态
> 这是**前期摸底**，不是实现教程。截至整理时（2026-11-17），环境盘点、源码结构、存储与权限机制的分析已完成，但媒体表、上传与播放接口、前端播放器、Docker 与 Nginx 配置**都还没动**。文中的「建议」「方向」是设计判断，不是已落地的功能；生产环境保持原状。

## 一、想做什么，以及不能碰什么

目标很朴素：在现有图床上增量增加视频、音频上传和网页在线播放能力。但约束比目标更重要：

| 目标 | 硬约束 |
| --- | --- |
| 支持视频 / 音频上传 | 保留原有图片上传、管理与图床功能 |
| 单视频上限 1GB | 不替换现有 PicFast，不影响正在运行的生产环境 |
| 网页在线播放 | 兼容现有用户认证、游客上传、用户组限制和存储策略 |
| 公开 / 私有访问权限 | 初期不做转码，先实现原文件上传、存储与播放 |
| 沿用现有权限体系 | 应用层支持大文件之前，不先改 Nginx 上传限制 |

一句话概括：**新增一条独立的媒体链路，原来的图片链路一行都不碰。**

## 二、先看清现有系统

摸底确认的技术栈：

| 层面 | 情况 |
| --- | --- |
| 后端 / 前端 | Go；React 19 + TypeScript + Vite |
| 数据库 / 数据访问 | PostgreSQL 16；SQLC |
| 迁移 | golang-migrate，SQL 文件嵌入程序，默认自动迁移 |
| 构建 | Docker 多阶段构建；Node 24 + pnpm 10.33.0 |
| 测试 | `make` 提供 `go test ./...`，`internal` 下约 70 个测试文件 |
| 版本基线 | 0.27.0 |

存储策略已经很丰富：Local、S3、腾讯 COS、阿里 OSS、七牛 Kodo、WebDAV，以及 TOS、OBS 等 S3 兼容策略。数据库里则有用户、用户组、存储策略、组与策略关联、图片、相册、API Token、审核、站点设置、审计日志、Webhook、标签等表。

认证方面，登录用户走 JWT 或 API Token（带读写 scope），游客上传走可选认证路径，用户组配置包含最大文件大小、允许扩展名、容量和上传频率限制；现有图片权限是公开 / 私有，私有图片未授权时通常返回 404。

前端也定位清楚了：登录用户上传页、游客上传页、`UploadZone`（目前只接受 `image/*`）、依赖图片尺寸与缩略图的 `UploadResultCard`、路由与控制台导航。本轮关键词扫描**没有发现现成的视频或音频播放器**——这只代表本轮没命中，还不能当成结论。

## 三、真正的拦路虎：存储接口是 `[]byte`

现有 `Storage` 接口长这样：

```go
type Storage interface {
    Write(ctx context.Context, path string, data []byte, contentType string) error
    Read(ctx context.Context, path string) ([]byte, error)
    Delete(ctx context.Context, path string) error
    URL(pathname string) string
    HealthCheck(ctx context.Context) HealthResult
    Close() error
}
```

Local 实现用 `os.WriteFile` / `os.ReadFile`，S3 上传用 `PutObject` 加 `bytes.NewReader(data)`、下载后把响应体整个读进内存，WebDAV 与 COS、OSS、Kodo 也基本是同一套 `[]byte` 模式。

> [!CAUTION] 1GB 文件不能整个进内存
> 图片业务这样写完全没问题，但换成 1GB 视频，峰值内存约等于文件大小乘以并发数；更关键的是，没有可寻址的分段读取，就做不了拖动进度条所需的 HTTP Range。这两点决定了媒体模块不能复用图片存储链路。

结论是：**保持旧 `Storage` 接口不变，新增独立的 `MediaStorage`**，提供流式写入、流式读取和可寻址的分段读取。本地存储可以用 `os.Open` 配合 `Stat`、`Seek` 和 `io.Reader` 做到低内存读取；S3 可以用 `GetObject` 的 Body 流和 Range 参数。COS、OSS、Kodo、WebDAV 的流式能力必须逐个核查，不能假设所有后端天然支持。

## 四、推荐架构：独立媒体模块

采用「保留原图片模块 + 新增独立媒体模块」的分层：

| 层次 | 职责 |
| --- | --- |
| 现有公共能力 | 用户、认证、权限、用户组、存储策略 |
| 原图片模块 | 保持现状，不改变图片上传与访问链路 |
| 新增媒体模块 | 媒体上传、元数据、权限、媒体管理、在线播放 |
| Media Service | 流式上传、文件校验、容量限制、哈希、失败清理 |
| Media Storage | 本地与对象存储的流式写入、读取及 Range 能力 |
| 数据库与文件存储 | `media_files` 元数据表及媒体文件实体存储 |

handler、service、storage、数据表全部独立，只在身份、用户组、容量和策略选择上共享现有逻辑。这样图片处理逻辑（EXIF、缩略图、图片处理）不会被媒体文件拖下水，媒体出问题也不会连累生产图床。

## 五、权限：最容易出事的地方

现有图片访问 `ServeImage` 的流程是：按 key 查记录 → 校验扩展名 → 检查审核状态 → 检查公开 / 私有 → 读取存储策略并拿到 Storage → `Read` 出完整 `[]byte` → 设置响应头 → 写入响应。权限测试确认：私有图片对匿名用户和其他普通用户返回 404，所有者和管理员可访问；公开图片所有人可访问；待审核或审核未通过的图片只有所有者和管理员能看。

媒体要沿用「公开 / 私有」的概念，但**访问鉴权必须独立实现**，尤其有三个坑：

- 游客记录可能没有普通 `user_id`，历史数据里 `images.user_id` 也可为空；
- 无效的显式凭证不能被意外降级成匿名访问；
- 私有媒体每次访问都要做权限检查，不能靠「URL 够难猜」来保护。

路由方面，现有 `/api/v1/images` 使用 `DualAuth` 加 `RequireScope("write")`，`/api/v1/upload` 用 `OptionalDualAuth`，图片访问 `/i/` 走 `OptionalAuth`（JWT 路径）。API Token 支持 `X-API-Token` 或 Bearer，在库里以 SHA256 hash 查找，scope 来自 JSON；`DualAuth` 先试 JWT 再试 Token，否则 401，`OptionalDualAuth` 在没有身份时允许继续匿名。

> [!WARNING] `RequireScope` 不等于业务授权
> 匿名路径会继续进入业务层。访客配置、容量、文件大小和频率限制必须在服务层自己落实，不能指望中间件替你做完。另外媒体读取端点是否支持 API Token，需要明确定义，别因为图片路由只用 `OptionalAuth` 就照抄。

## 六、数据库与迁移

建议新增独立的 `media_files` 表，记录媒体 ID、用户 / 用户组 / 策略 ID、对象 key 与 path、原始文件名、大小、MIME、扩展名、媒体类型、时长、权限和时间戳。

现有机制已经摸清：迁移文件成对使用 `.up.sql` / `.down.sql`，编号当前到 `036`，下一组应为 `037`；`migrations/embed.go` 用 `//go:embed *.sql` 把 SQL 嵌进二进制；后端用 golang-migrate 配合 pgx/v5 与 iofs，启动时按 `PICFAST_DATABASE_AUTO_MIGRATE` 决定是否自动迁移——设成 `false` 就可以先手动执行 `picfast migrate`。SQLC 侧由根目录 `sqlc.yaml` 配置，查询在 `internal/sqlc/queries`、schema 取 `migrations`、Go 代码输出到 `internal/sqlc`、driver 为 `pgx/v5`；`make generate` 生成代码，`check-generated` 会检查生成结果是否产生 Git diff。

**目前这些全都还没做**：没有建表、没有新迁移、没有跑过代码生成。设计时也别想当然——不能假定图片的 `image_num` 计数器能直接当媒体计数器，图片与媒体是否共享用户总容量、访客配额怎么算，都要先定义清楚。

还有个容易忽略的细节，现有策略列表查询是：

```sql
SELECT s.* FROM strategies s
JOIN group_strategies gs ON s.id = gs.strategy_id
WHERE gs.group_id = $1;
```

> [!TIP] 别依赖数据库的行顺序
> 这条 SQL 没有 `ORDER BY`，所以「取第一条」并不稳定。媒体服务要明确写出自己的策略选择规则，而不是继承这个隐含假设。

## 七、播放体验的关键：HTTP Range

上传能用和播放好用是两件事。在线播放至少要正确处理 `GET`、`HEAD`、`Range`、`206 Partial Content`、`Content-Range`、`Accept-Ranges`、`If-Range`；本地文件可以考虑文件句柄配合 `http.ServeContent`，对象存储则按后端实现流式读取或 Range 请求。响应还要给对 `Content-Type`，并设置适合在线播放的 `Content-Disposition: inline`。

建议支持的格式：

| 类型 | 格式 |
| --- | --- |
| 视频 | MP4、WebM、MOV、MKV |
| 音频 | MP3、WAV、FLAC、M4A、AAC、OGG |

> [!NOTE] 允许上传 ≠ 浏览器能播
> 扩展名和 MIME 放行，只代表服务端肯收。初期优先验证 MP4（H.264/AAC）和常见音频格式；MOV、MKV 以及部分编码组合的浏览器兼容性要单独测。

## 八、运营层面的硬约束

这台机器大致是 4 核 / 4GB 内存、60GB SSD（可用约 50GB）、5Mbps 公网带宽、每月 500GB 流量，Nginx 当前 `client_max_body_size` 为 `100M`。这些数字直接决定了设计取舍：

- 初期不转码，就要明确告诉自己「原始文件播放」在 5Mbps 下是什么体验；
- 流式传输**只降低服务端内存占用，不会减少播放实际消耗的数据量**，500GB 月流量仍是硬上限，需要流量统计与访问控制，避免公开链接被滥用；
- Nginx 的 body size、代理超时、请求缓冲和临时目录空间，等应用层大文件能力稳定后再一起调整；
- 大文件进入备份后，对磁盘和网络的影响要重新评估。

## 九、风险清单

| 风险 | 应对方向 |
| --- | --- |
| 大文件导致内存占用过高 | 流式上传与读取，限制并发和临时文件占用 |
| 视频无法拖动或跳转 | 实现 HTTP Range、HEAD 与正确的长度 / 范围响应头 |
| 带宽限制影响体验 | 初期不转码，明确原始文件播放的限制 |
| 月流量被公开链接耗尽 | 增加流量统计与访问控制 |
| 私有媒体泄露 | 独立实现访问鉴权，默认拒绝未授权访问 |
| 游客滥用上传 | 复用容量、大小、频率限制并增加并发约束 |
| 对象存储 Range 能力不一致 | 逐个后端验证，不假设天然支持 |
| 数据库与文件不一致 | 设计上传完成标记、失败清理与孤儿文件处理 |
| 大文件上传超时 | 媒体服务稳定后再统一调整 Nginx 相关配置 |

## 十、实施顺序

1. 从固定版本创建功能分支，保留当前提交作为开发基线。
2. 新增 `media_files` 迁移与 SQLC 查询，先在测试库验证。
3. 实现 `MediaStorage` 接口，先做本地存储与单元测试。
4. 实现上传服务：流式写入、大小 / 扩展名 / MIME 校验、流式哈希、配额与失败清理。
5. 实现登录用户与游客媒体上传 API，覆盖认证、scope、容量和权限测试。
6. 实现读取接口，支持 GET、HEAD、Range 和私有访问控制。
7. 开发前端媒体上传页、结果卡片、视频 / 音频播放器、管理页与导航入口。
8. 增加 Docker 媒体目录挂载（核对容器 UID/GID 权限）与备份策略。
9. 调整 Nginx 上传大小与代理超时。
10. 跑 Go 测试、SQLC 生成检查、前端 lint / typecheck / build 和容器构建。
11. 先在独立测试环境验证并做真实大文件测试，再谈生产部署。

上传实现上还有几条原则值得提前写下来：用 `io.LimitReader` 之类机制在服务端实际计数，不能只信客户端的 `Content-Length`；扩展名不能作为唯一校验依据；用临时文件加原子提交，数据库写失败时清理已写入的对象；日志里绝不输出 API Token、JWT Secret、数据库密码或管理员凭据。

## 十一、进度与下一步

**已完成**：生产环境与容器状态核查、镜像版本与源码基线核对、固定版本源码克隆、媒体目录创建（尚未挂载到容器）、生产数据备份与校验、存储接口与策略选择分析、部分路由认证与图片权限分析、迁移与 SQLC 生成机制确认、前端关键文件定位。

**仍待检查**：SQLC 配置与生成流程的全量确认、迁移文件命名与执行工具、前端上传实现逐段阅读、媒体路由归属与中间件组合、访客身份 / 用户组 / 默认策略的完整上下文、每个云存储后端的流式与 Range 能力、Dockerfile 构建与媒体挂载、测试与部署更新流程。

> [!CAUTION] 备份校验通过 ≠ 一定能恢复
> 数据库 dump 的格式、文件归档清单、SHA256 校验和都验证过了，但还没做独立环境的完整恢复演练，备份也仍在同一台服务器的磁盘上。动手改代码之前，这两项应该先补上。

安全现状是清楚的：生产应用、数据库、Compose 和 Nginx 都还没有因为媒体改造被修改，媒体目录建了但没挂载。下一步就是建功能分支，然后从数据库迁移开始。

这类改造里，最值钱的结论往往写在第一行代码之前。先把「绝对不能动的东西」圈出来，比急着给上传页加一个视频图标重要得多。
